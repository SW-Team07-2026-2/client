## 2. 호출 래퍼 — 모든 API 가 이걸 거칩니다

26 §0-7 예시를 그대로 쓰면 됩니다. 지켜야 할 것만:

| # | 규칙 | 안 하면 |
| --- | --- | --- |
| 1 | `fetch(..., { credentials: "include" })` | 쿠키가 안 실려 전부 401 |
| 2 | POST · PUT · PATCH · DELETE 에 `X-XSRF-TOKEN` (G3 의 `xsrfToken`) | 403 `CSRF_*` |
| 3 | 응답 봉투 `{ isSuccess, code, message, result, correlationId }` — 분기는 `code` 로 | — |
| 4 | **본문이 JSON 이 아닐 수 있음** — Cloudflare 가 막으면 403 · 429 HTML | `res.json()` 예외로 화면이 죽음 |
| 5 | 401 → `POST /api/auth/refresh` **1번만** → 성공하면 원래 요청 재시도 | 무한 재시도 · 불필요한 로그아웃 |
| 6 | 503 `SERVICE_UNAVAILABLE` 은 `result.service` 로 어느 서비스인지 옴 — 로그아웃하지 말고 “잠시 후 다시” | — |
| 7 | 버그 제보 때 `correlationId` 를 같이 | 백엔드가 로그를 못 찾음 |

## 3. 앱 시작 — 로그인 상태

```
앱 로드 → G3 GET /api/auth/me
 ├─ 200 → 로그인 상태 · xsrfToken 보관 · nickname · profileImageUrl 표시
 │        (stale: true 면 회원 서비스 장애 — 이름 · 사진만 비고 로그인은 유지)
 └─ 401 → 래퍼가 G5 1회 → 200 이면 G3 다시 → 로그인 상태
                      └→ 401 이면 비로그인 (정상 — 공개 화면 그대로)
```

- `xsrfToken` 은 메모리에 두고, 새로고침하면 G3 로 다시 받습니다.
- 🔒 표시 API 는 비로그인이면 부르지 말고 로그인 버튼을 보여 주세요.

## 4. 로그인 · 가입

### 4-1. 로컬 — 가짜 로그인

```tsx
// 개발용 버튼에만 — 운영 Gateway 에는 없음 (404)
const r = await fetch(`${BASE}/dev/login?nickname=${encodeURIComponent(name)}`, { credentials: "include" });
// 기존 회원 → 쿠키 3종 · 처음이면 SIGNUP 쿠키 → /signup 화면으로 (아래 4-2 의 가입 흐름 그대로 — 약관 동의부터)
```

- 같은 닉네임은 같은 회원입니다. **약관 화면을 다시 보려면 새 닉네임**으로 로그인하세요 (처음인 사람만 `/signup`).

### 4-2. 운영 — 카카오

```
「카카오로 시작하기」 → location.href = BASE + "/oauth2/authorization/kakao"   ← G1 · fetch 아님
  → 카카오 동의 화면 (닉네임 · 이메일) → (Gateway 가 콜백 G2 처리 — 프론트는 부르지 않음)
  ├─ 기존 회원 → 302 /         → §3 (G3)
  ├─ 처음     → 302 /signup    → ① 약관 동의
  └─ 실패 · 취소 → 302 /login

/signup — 아직 회원 아님 · G3 은 401 · 🔒 API 불가
  ① 약관 동의 ✏️ 11/05
     M24 GET /api/members/terms → items 를 순서대로 체크박스 (required → [필수] · 아니면 [선택] · 문구는 title)
     「전체 동의」 · 항목별 체크 · 「보기」 = content(마크다운)를 그 자리에서 펼침
     필수를 다 체크해야 「다음」 → 체크 결과는 메모리에만 (서버 호출 없음)
  ② 밴드 고르기
     X4 GET /api/chatbot/artists/similar           ← 첫 세트 · 보여 준 id 를 shown 에 모음
     밴드를 처음 누르면 X4 ?artistId={id}&exclude={shown}&size=3 → 「○○와 비슷한 밴드」 (선택은 화면에서만)
  ③ 「완료」 · 「건너뛰기」 → G13 POST /api/auth/signup   (X-XSRF-TOKEN — XSRF-TOKEN 쿠키 값)
       { artistIds, agreements: items.map(t => ({ termsId: t.termsId, agreed: checked[t.termsId] })) }
    ├─ 200 → 회원 생성 · AT · RT 쿠키 → 홈 → G3
    ├─ 409 TERMS_OUTDATED → "약관이 바뀌었어요" → M24 다시 → ① 부터 (사인업 토큰은 그대로)
    ├─ 400 REQUIRED_AGREEMENT_MISSING → 화면 버그 (필수 체크 없이 「다음」이 열림)
    └─ 401 SIGNUP_EXPIRED · SIGNUP_INVALID → "가입 시간이 지났어요" → G1 다시
```

- 🔴 **X4 는 챗봇 API 라 지금 503 입니다** (챗봇 미배포). 503 이면 밴드 목록 대신 **「건너뛰기」만** 보여 주세요 — `G13 { artistIds: [], agreements }` 는 챗봇 없이 됩니다.
- `termsId` 는 M24 응답 값을 그대로 씁니다 — 숫자를 코드에 박지 마세요 (약관이 바뀌면 id 가 바뀜).
- ②에서 새로고침하면 ①의 체크가 사라집니다 → ①부터 다시. ①과 ②를 한 화면(단계 전환)으로 두면 편합니다.
- 화면 경로 `/` · `/signup` · `/login` 은 Gateway 가 돌려보내는 주소라 이름을 바꾸면 백엔드도 바꿔야 합니다 (28 §7 ①).
- 가입 중간에 나가면 아무것도 저장되지 않습니다. 사인업 토큰은 30분.
- ✏️ 11/06 푸터 화면은 **M25** `GET /api/members/terms/{code}` (공개 · `{ termsId, code, version, title, content, required }` 하나) — 「이용약관」 `TOS` · 「개인정보처리방침」 `PRIVACY_POLICY`. 🔴 M24 의 `PRIVACY` 는 가입 **동의서**이고 처리방침은 **다른 문서**입니다 — 처리방침 링크에 `PRIVACY` 를 쓰지 마세요.

## 5. 토큰 재발급 · 로그아웃

| 상황 | 처리 |
| --- | --- |
| AT 만료 5분 전 | Gateway 가 응답 `Set-Cookie` 로 알아서 갱신 — 프론트 할 일 없음 |
| 보호 API 401 | 래퍼가 G5 1회 (§2 규칙 5) |
| G5 401 `REFRESH_INVALID` · `REFRESH_REUSED` | 로그인 화면 |
| G5 503 | 쿠키 유지 · “잠시 후 다시” (로그아웃 아님) |
| 로그아웃 | G4 `POST /api/auth/logout` (X-XSRF-TOKEN · 항상 200) → 상태 초기화 → G3 401 확인 |

## 7. 굿즈 · 음반 구매

### 7-1. 주문

```
C8 상품 확인 (가격 · 재고)
M19 배송지 — 기본 배송지 미리 선택 · 「변경」 · 「새 주소」 (+ 저장하면 M20)
    배송지가 하나도 없으면(첫 결제) 입력칸만 → M20 { …, isDefault: true }
 └▶ C9 POST /api/catalog/orders { items, shipping } → { orderId, amount, pgOrderId: "GOODS-…", expiresAt }
     └▶ 토스 결제창 (7-2) — 10분 안에 승인까지
```

### 7-2. 토스 결제창

26 §5-0 코드 그대로 — `orderId` 에 **`pgOrderId`**, 금액은 응답의 `amount` 그대로. 굿즈 · 티켓이 같은 결제창 · 같은 결과 화면을 씁니다.

결제창을 열기 전에 결과 화면이 무엇을 승인할지 남겨 두세요 (권장):

```tsx
sessionStorage.setItem(`pay:${pgOrderId}`, JSON.stringify({ kind: "goods", id: orderId }));     // 굿즈 — C9 응답
sessionStorage.setItem(`pay:${pgOrderId}`, JSON.stringify({ kind: "ticket", id: bookingId }));  // 티켓 — N10 응답
```

### 7-3. 결제 결과 화면 — `/payments/success` · `/payments/fail`

```
/payments/success ?paymentKey&orderId&amount     ← orderId = pgOrderId
  ctx = sessionStorage["pay:" + orderId]          (없으면 pgOrderId 앞부분 GOODS- / TICKET- 로 구분)
  ├─ 굿즈  → P1 POST /api/payments/confirm { paymentKey, orderId, amount }    ← 쿼리 3개 그대로
  │          ├─ APPROVED → C11 주문 상세 (CONFIRMED)
  │          ├─ DECLINED → reason 표시 · 「다시 결제」 또는 C12 취소
  │          └─ 409 PAYMENT_EXPIRED → 다시 주문
  └─ 티켓  → N16 POST /api/concerts/bookings/{bookingId}/confirm { paymentKey, amount }   → §8-3

/payments/fail ?code&message
  → 승인 API 를 부르지 않음 · message 표시 · 「다시 결제」 = 같은 pgOrderId · amount 로 requestPayment
```

- 결과 화면은 새로고침 · 뒤로가기로 두 번 열릴 수 있습니다 — 승인 API 를 부르기 전에 버튼 · 로딩으로 중복 호출을 막아 주세요.
- 테스트 키로는 카카오페이 · 페이코가 안 됩니다 — 시연은 카드 · 토스페이. 가상계좌는 결제 UI 에서 빼기.

## 8. 공연 예매

### 8-1. 대기열 (`queueEnabled: true` 공연만)

```
N2 공연 상세 → queueEnabled ?
 ├─ true  → N4 POST /api/concerts/{id}/queue
 │          → N5 GET …/queue/status 를 pollAfterMs 마다 → ADMITTED { entryToken }
 │          (페이지를 나가면 N6 DELETE …/queue)
 └─ false → 바로 8-2
```

- 🔴 대기 화면에 **“화면을 나가면 순번이 사라집니다”** — N5 폴링이 하트비트라 15초 끊기면 빠집니다 (백그라운드 탭 포함).
- `entryToken` 은 N10 의 `X-Entry-Token` 헤더에만 씁니다.

### 8-2. 좌석 선점

```
N7 GET /api/concerts/{id}/seats      ← AVAILABLE 만 고를 수 있음 · HELD · SOLD 는 회색
 └▶ 「선택완료」 → N10 POST /api/concerts/{id}/bookings { seatId }   [+ X-Entry-Token]
      → { bookingId, amount, pgOrderId: "TICKET-…", expiresAt, expiresIn }   ← 선점 성공 · 8분 타이머 시작
      ├─ 409 SEAT_TAKEN  → "이미 선택된 좌석입니다" · N7 새로고침
      └─ 409 HOLD_EXISTS → 내 선점이 다른 좌석에 있음 → result.bookingId 로 N13 후 다시 (또는 그 선점으로 결제)
```

**선점 타이머** — 26 N10 “선점 타이머 프론트 규칙” 6가지를 그대로 따릅니다. 요점:

- `sessionStorage["booking:{bookingId}"] = Date.now() + expiresIn * 1000` (`expiresAt` 아니고 `expiresIn` 기준)
- 🔴 토스 결제창으로 넘어갈 때 **지우지 않기** — 돌아왔을 때 타이머가 없어집니다
- 값이 없으면 N12 의 `expiresIn` 으로 한 번 복구 · 남은 시간을 폴링하지 않기
- 「취소」 · 「좌석 다시 고르기」는 **N13 `POST /api/concerts/bookings/{id}/cancel`** — 안 부르면 그 좌석이 9분 동안 남에게 회색

### 8-3. 결제 → 승인

```
「결제하기」 → 토스 결제창 (§7-2 · orderId = pgOrderId) → /payments/success (§7-3)
  └▶ N16 POST /api/concerts/bookings/{bookingId}/confirm { paymentKey, amount }   ← amount = N10 의 amount
       ├─ CONFIRMED                 → 타이머 삭제 → N12 예매 상세 → 모바일 티켓 (§9)
       ├─ PENDING (DECLINED)        → reason 표시 · 응답의 새 pgOrderId 로 결제창 다시 (선점 · 타이머 그대로)
       ├─ EXPIRED · 410 HOLD_EXPIRED → "선점 시간이 끝났어요" · 타이머 삭제 → N7 (돈 안 나감)
       ├─ 409 ALREADY_PAID · SEAT_LOCKED → N12 로 상태 확인
       └─ 503 PAYMENT_PENDING       → N12 로 결과 확인 — 🔴 다시 결제하지 않기
```

선점 풀기 · 예매 취소 · 환불은 모두 N13 하나입니다 (결제된 티켓 취소는 공연 24시간 전까지).

## 9. 모바일 티켓 · 입장 QR

```
MY › 예매 내역 N11 → N12 예매 상세 (공연 · 좌석 · 예매번호)
  모바일 티켓 열기 → N17 GET /api/concerts/bookings/{id}/entry-qr → { token, expiresAt }
    → token 을 그대로 QR 로 그림 + "nn초 뒤 새 QR" → 20초마다 N17 다시
    ├─ 409 ENTRY_NOT_OPEN     → "HH:mm 부터 열려요" (result.opensAt · 공연 3시간 전)
    ├─ 409 ALREADY_CHECKED_IN → "입장 완료 HH:mm" (result.checkedInAt) · QR 없음
    └─ 409 ENTRY_CLOSED       → "입장 시간이 지났어요"
  티켓을 닫거나 화면이 안 보이면 타이머 멈춤
```

- QR 은 프론트가 만들지 않습니다 — N17 의 `token` 만. 「QR 저장」 없음 (30초 뒤 무효). 티켓은 배송이 없습니다.
- 굿즈 주문은 MY › 주문 내역 C10 → C11, 결제 내역은 P2 → P3.

## 10. 운영 확인 — Vercel 도메인 연결 뒤

인프라 담당이 Vercel 레코드를 Cloudflare 에 넣고 `https://indig.co.kr` 이 뜬 다음에 (28 §6):

- [ ]  공연 · 카탈로그 목록이 뜸
