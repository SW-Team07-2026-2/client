### ① 예매 — 자체 구현

외부 링크만으로는 HPA·분산 락·부하 테스트라는 기술적 핵심이 전부 사라져 단순 CRUD 아카이브가 되므로, **자체 예매 시스템**으로 확정했습니다.

```
좌석 조회 → 좌석 점유(HELD, 분산 락) → 더미 결제 → 예매 확정(PAID)
                                           실패 시 ↓
                                      좌석 점유 보상 해제
```

### ③ 데이터 수집 — k8s CronJob

AI Service 내부에 두면 크롤링 부하가 추천 응답에 영향을 주므로 분리했습니다. **Job 은 실행 중에만 메모리를 점유하므로 노드 상주 메모리가 0** 입니다.

| Job | 소스 | 주기 |
| --- | --- | --- |
| `spotify-sync` | Spotify API | 일 1회 |
| `concert-crawler` | Indiego | 일 1회 |
| `stock-sync` | L Pick · Yes24 | 1시간 |

**CronJob 은 DB 에 직접 쓰지 않습니다.** Catalog Service 의 내부 전용 REST 를 거쳐야 스키마 소유권이 유지되고 이벤트도 함께 발행됩니다.

### ④ 알림 — 아티스트 단위 저장

구독자별로 레코드를 만들지 않습니다. **신보 1건 = `activity` 1행**이며, 분배는 조회 시 `follow` JOIN 으로 일어납니다.

```
Catalog  album.released (title·thumbnail 포함)
   ↓
Member   activity 1행 적재          ← 구독자 수와 무관
   ↓
조회     follow JOIN + occurred_at > followed_at
배지     occurred_at > last_seen_at 카운트 (Redis 캐시 TTL 30초)
```

### 🆕 ⑩ 로그인 — OAuth 전용

가입과 로그인은 **카카오 · Google 계정으로만** 합니다. 처음 로그인하면 자동으로 가입되며, 서비스는 비밀번호를 저장하지 않습니다.

```
프론트   [카카오로 시작하기] → GET /api/auth/oauth2/authorize/kakao
   ↓     카카오 동의 화면
Member   GET /api/auth/oauth2/callback/kakao?code=…&state=…
         state 검증 → 토큰 교환 → 사용자 정보 조회
         (provider, provider_id) 로 users 조회 · 없으면 생성
   ↓     프론트로 리다이렉트  /oauth/callback?code=<1회용 코드>
프론트   POST /api/auth/token { code } → Access + Refresh Token · isNewUser
```

| 결정 | 이유 |
| --- | --- |
| 사용자 식별은 **`(provider, provider_id)`** | 카카오는 이메일 동의가 선택일 수 있어 이메일이 없을 수 있음 |
| JWT 는 URL 에 싣지 않고 **1회용 코드**로 교환 | URL 은 브라우저 기록·로그·Referer 에 남음. 코드는 Redis TTL 60초 · 1회 사용 |
| OAuth `state` 는 세션이 아닌 **쿠키**에 저장 | Member replica 가 2개이고 ALB sticky 를 쓰지 않으므로, 콜백이 다른 Pod 로 가면 세션 기반은 실패함 |
| 카카오 ↔ Google **계정 연결 없음** | 같은 사람이 두 방식으로 들어오면 계정 2개. 이메일로 자동 병합하지 않음 |
| OAuth 경로를 `/api/auth/oauth2/*` 로 변경 | Spring 기본 경로(`/oauth2/*`, `/login/oauth2/*`)는 ALB 의 `/api/auth/*` 규칙에 걸리지 않음 |

### 🆕 ⑪ 정책 값 (10/8 확정)

| 정책 | 값 | 이유 |
| --- | --- | --- |
| 1인 좌석 한도 | **공연별 1석** | 좌석 독점 방지 · 여러 좌석을 순서대로 잠그는 문제가 사라져 구현 단순 |
| 좌석 점유 시간 | **3분** | 입장 토큰(10분) 안에 결제까지 끝남 |
| 예매 취소 | **공연 시작 24시간 전까지** · 더미 전액 환불 | — |
| Access Token | **30분** | 로그아웃은 Gateway 블랙리스트로 즉시 차단 · 인증 Redis 장애(fail-open) 때만 30분이 상한 |
| Refresh Token | **14일** · 재발급 때마다 교체 | 탈취된 Refresh 재사용 탐지 |

### 🆕 ⑫ API Gateway — Spring Cloud Gateway (10/8 확정)

기업 과제명("AI와 Spring Cloud 모듈을 활용한 MSA")에 맞추면서 k3s 의 장점(Pull GitOps · Pod HPA · 재스케줄)은 유지하기 위해, Eureka 스택 전체 대신 **Gateway 와 Kubernetes 디스커버리**만 채택했습니다.

```
클라이언트 → ALB (규칙 1개 /api/*) → Gateway × 2 (AZ-b · AZ-c)
          → CORS → X-Request-Id → JWT 검증 → 블랙리스트 → (AI) 호출 한도
          → lb://member · catalog · concert · ai   (Spring Cloud Kubernetes 가 k8s API 에서 Pod 목록 수신)
          → GET 실패 시 다른 Pod 로 최대 2회 재시도
```

| 결정 | 이유 |
| --- | --- |
| 실패한 GET 을 다른 Pod 로 재시도 | ALB 는 노드까지, kube-proxy 는 주소 변환뿐이라 재시도 불가 |
| 블랙리스트를 Gateway 에서 조회 | 로그아웃 즉시 차단 · 업무 서비스는 Member 의 Redis 를 읽지 않음 |
| 업무 서비스는 ClusterIP 전용 | 외부에서는 Gateway 를 거쳐야만 닿음 · `/internal/**` 은 Gateway 가 404 |
| Eureka 미사용 | k8s Service · EndpointSlice 가 레지스트리 역할 — 추가 Pod 불필요 |

### 4.1 데이터베이스 소유권 — ✏️ 단일 PostgreSQL · 스키마 분리 + 권한 격리 (10/15)

**✏️ 10/15 — 물리 분리에서 권한 격리로.** 인스턴스는 `db.t4g.medium`(2 vCPU · 4 GiB) **1대**이고, 서버스마다 스키마와 전용 유저를 둘니다.

```sql
GRANT USAGE ON SCHEMA member TO member_svc;   -- 자기 스키마만
ALTER ROLE member_svc CONNECTION LIMIT 15;    -- 15/20/30/15/10 = 합계 90
-- 타 스키마 JOIN 시도 → ERROR: permission denied for schema catalog
```

얻는 것 — 경계가 문서가 아니라 **DB 가 강제**합니다. 한 서버스가 커넥션을 다 쓰는 사고도 역할별 상한으로 막힙니다 (합계 90 ≪ `max_connections` ≈ 450).

🔴 잘는 것 — **CPU·I/O 격리는 사라지고 되돌릴 수 없습니다.** 티켓팅 부하가 같은 2 vCPU 를 크롤러·HNSW 인덱싱과 나눔니다. → 크롤러 CronJob · 대량 임베딩 삽입은 **티켓팅 시간대 금지**가 운영 제약으로 들어옵니다.

🔴 HikariCP 풀은 **10 → 5** 로 내립니다. PostgreSQL 은 커넥션당 프로세스(≈ 7 MB)라, 110개면 ≈ 770 MB · 55개면 ≈ 385 MB 입니다 — 4 GiB 에서는 이 차이가 충분히 큽니다.
